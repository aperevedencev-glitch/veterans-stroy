# eis2nostroy — сведения о договорах членов СРО из ЕИС в НОСТРОЙ

Модуль каждый день забирает из ЕИС договоры членов СРО по 44-ФЗ, 223-ФЗ и ПП РФ 615, сверяет их с другими источниками, присваивает каждой записи статус и готовит пакет для передачи в НОСТРОЙ. Оператор получает Excel, где сразу видно, что передать, а что требует решения.

## Как это работает

1. **ЕИС.** Официальный сервис отдачи информации (getDocsLE для юрлица, getDocsIP для физлица) по токену пользователя машиночитаемых данных. Сервис не ищет по ИНН поставщика, он отдаёт архивы документов за день по региону заказчика. Модуль скачивает архивы реестров RGK (контракты 44-ФЗ), RD223 (договоры 223-ФЗ) и RD615 (договоры ПП РФ 615) и оставляет только договоры, где поставщик — член СРО.
2. **Дополнительные источники** (необязательно, файлы CSV/XLSX):
   - выгрузка «Финподдержки»;
   - уведомления членов о договорах по регламенту;
   - выгрузка уже переданных сведений из Единого реестра НОСТРОЙ.
3. **Сверка.** Записи разных источников сопоставляются по реестровому номеру, номеру извещения, а без номеров — по ИНН заказчика, дате (±3 дня) и цене (±1 %).
4. **Статусы.**

| Статус | Когда | Действие оператора |
|---|---|---|
| Подтверждён | договор найден в ЕИС, источники совпадают | передать в НОСТРОЙ |
| Вероятный | есть только в «Финподдержке» (протокол) | запросить подтверждение у члена |
| Расхождение | источники расходятся по сумме или дате | выбрать верное значение |
| Заявлен членом | есть только в уведомлении члена | проверить документы |
| Уже в НОСТРОЙ | сведения уже в Едином реестре | ничего |
| Вне периода | договор раньше начала периода сверки | не передавать |

Период: конкурентные договоры — с даты уровня ОДО члена, но не ранее 01.07.2017; неконкурентные — с 01.03.2026. Даты меняются в `config.toml`.

5. **Выгрузки** в папке `data/out`:
   - `sverka_ГГГГММДД.xlsx` — для оператора: «Сводка», «К передаче», «Требуют решения», «Все записи»;
   - `nostroy_*.csv` и `nostroy_*.json` — только подтверждённые договоры для загрузки в НОСТРОЙ.
6. **Оповещения** об итогах и сбоях — в Telegram и/или на почту.

## Договоры 223-ФЗ через протоколы закупок

В карточках договоров 223-ФЗ, заключённых с 2019 года, поставщик в открытых данных ЕИС не указан. Поэтому поиск по ИНН поставщика находит договоры членов только до 2018 года. Победитель с ИНН есть в протоколе закупки, а договор ссылается на протокол. Модуль собирает договоры 223-ФЗ в два шага:

1. **Протоколы** (поток `kind = "protocol"`). Модуль разбирает протоколы и запоминает, где член СРО занял первое место, где с ним заключён договор или где его заявка была единственной допущенной. Победы копятся в `data/work/protocol_wins.jsonl`.
2. **Договоры.** Договор 223-ФЗ без поставщика связывается с победой по `protocolInfoGuid`, а если его нет — по паре «номер извещения + лот». Цена, даты и номер берутся из последней редакции договора.

Победа без найденного договора попадает в сверку со статусом «Вероятный»: договор мог быть ещё не заключён или не опубликован.

Проверено на настоящих данных ЕИС: закупка № 32414075550, итоговый протокол № 32414075550-03, договор № 53435098928240001840000 ООО «ЛУКОЙЛ-ВОЛГОГРАДЭНЕРГО», победитель ООО «ВОЛГОГРАДМОНТАЖ» (тесты `tests/test_protocols.py`).

Протоколы 223-ФЗ скачиваются по всем регионам (`regions = ["all"]`), договоры — только по регионам заказчиков, у которых члены побеждали (`regions = ["wins"]`). Ежедневный прогон — около 100–150 запросов, в пределах лимита ЕИС 5000 запросов в час. Загрузка истории за год — примерно 30–35 тысяч запросов, это 9–10 часов; прерванную загрузку можно запустить снова, скачанные дни не повторяются. Историю удобнее догружать по годам, начиная со свежих:

```bash
python -m eis2nostroy fetch --from 2026-01-01 --to 2026-10-21
python -m eis2nostroy fetch --from 2025-01-01 --to 2025-12-31
```

Перед первым запуском сверьте с инструкцией ЕИС код подсистемы закупок 223-ФЗ (в примере — `RI223`) и типы документов протоколов. Если код или тип не подойдут, ЕИС вернёт ошибку, модуль запишет её в лог и в оповещение и продолжит остальные потоки.

## Установка

Нужен Python 3.11 или новее.

```bash
pip install -r requirements.txt
cp config.example.toml config.toml
```

В `config.toml` укажите путь к списку членов, регионы заказчиков и настройки оповещений. Токен ЕИС лучше передать переменной окружения:

```bash
export EIS_TOKEN="токен из личного кабинета ЕИС"
```

Список членов — XLSX или CSV со столбцом «ИНН». Желательно добавить «Наименование» и «Дата присвоения уровня по ОДО». Подходит лист «Члены» из шаблона сверки.

## Запуск

```bash
# история за период (первичная загрузка)
python -m eis2nostroy fetch --from 2026-03-01 --to 2026-10-15

# архивы, скачанные заранее (например, за прошлые годы)
python -m eis2nostroy import-archives --law 44 data/archives/44

# сверка и выгрузки
python -m eis2nostroy reconcile

# ежедневный прогон: последние 3 дня + сверка + оповещение
python -m eis2nostroy run --days 3
```

Ежедневный запуск по расписанию (cron, 06:30):

```
30 6 * * * cd /opt/eis2nostroy && EIS_TOKEN=... python3 -m eis2nostroy run --days 3 >> data/run.log 2>&1
```

На Windows — через «Планировщик заданий» с той же командой.

Скачанные архивы кэшируются в `data/cache`, повторный запуск за тот же день не обращается к ЕИС. Между запросами выдерживается пауза (`min_interval_sec`): лимит сервиса — 5000 запросов в час.

## Что нужно сделать перед работой с реальными данными

1. **Получить токен.** Зарегистрировать Ассоциацию в ЕИС как пользователя машиночитаемых данных (через ЕСИА) и выпустить токен.
2. **Сверить параметры сервиса с XSD ЕИС** (`getDocsLE`/`getDocsIP`, Альбом ТФФ): имя элемента токена для юрлица (`token_header`), значения `documentType44`/`documentType223` для договоров в подсистемах RGK, RD223, RD615. В `config.example.toml` они вынесены в настройки, код менять не нужно.
3. **Пробный прогон за один день** по одному региону: `fetch --from Д --to Д`, затем открыть `data/work/eis_contracts.jsonl` и проверить, что поля договоров (номер, дата, цена, заказчик) заполнены. Разбор XML устойчив к изменениям схем, но первый прогон на реальных архивах стоит проверить глазами.
4. **Регионы.** В `regions` перечислить коды регионов заказчиков, с которыми работают члены СРО. Договор с заказчиком из не указанного региона модуль не увидит.
5. **Передача в НОСТРОЙ.** Пока спецификации API НОСТРОЙ для СРО нет, модуль готовит CSV/JSON для загрузки оператором. Когда спецификация появится, реализуйте `NostroyTransport.send_api()` в `eis2nostroy/nostroy.py` и переключите `mode = "api"`.

## Тесты

```bash
pip install pytest
python -m pytest -q
```

Тесты используют вымышленные ИНН и синтетические XML. Они проверяют разбор архивов (в том числе вложенных), запросы к ЕИС с повтором при неготовом архиве, кэш, все статусы сверки и сквозной прогон до выгрузок.

## Структура

```
eis2nostroy/
  config.py      настройки
  members.py     список членов СРО
  eis_client.py  запросы к ЕИС, скачивание архивов, кэш
  parser.py      разбор XML договоров, отбор по ИНН членов
  sources.py     файлы «Финподдержки», уведомления, реестр НОСТРОЙ; хранилище
  reconcile.py   сопоставление и статусы
  export.py      Excel для оператора, пакет для НОСТРОЙ
  nostroy.py     передача в НОСТРОЙ (файл / API)
  alerts.py      Telegram и почта
  cli.py         команды fetch, import-archives, reconcile, run
```
